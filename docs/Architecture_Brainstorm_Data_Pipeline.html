1. The Core Problem: PDF Protocols → Executable Intelligence

The fundamental engineering challenge of this thesis is bridging the gap between static protocol documents (PDFs, flowcharts, SOPs) and an AI system that can train people on those protocols inside VR.

What We Have

PDFs that say things like: "Step 1: Check if patient can walk → if yes, tag MINOR."

56 identified protocol sources across 12 domains — the vast majority in PDF format, with only 3 having extractable JavaScript decision logic (CHEMM-IST, REMM, WISER).

What We Need the System to Do

  1. Generate a VR scene where a specific protocol applies (scenario generation)
  2. Watch the trainee in real-time and track their every action against the protocol (compliance monitoring)
  3. Detect errors: "You skipped step 3 and made the wrong call at decision point 2" (rule enforcement)
  4. Provide grounded feedback citing actual protocol text (evidence-based debriefing)
  5. Adapt the next scenario based on what the trainee got wrong (intelligent tutoring)
🎓 Thesis Contribution: This gap — PDF → executable protocol intelligence — is where the thesis contribution lives. Nobody has built this pipeline for emergency response protocols yet. The literature review confirmed: zero open-source repositories provide emergency protocols in standardized machine-readable format designed for AI consumption.

2. Three Possible Approaches (Evaluated)

Approach A Pure Rule Engine (Manual Extraction)

Extract every protocol by hand into JSON decision trees → build a finite-state machine (FSM) that checks compliance.

✓ Pros:
Deterministic, explainable, no hallucinations. Every check is traceable to a specific rule.
✗ Cons:
Doesn't scale. 60+ NASEMSO protocols × manual conversion = months of work. Brittle — any protocol update means re-engineering. No natural language interaction.

Verdict: Viable for a single protocol proof-of-concept but not sustainable as the system grows.

Approach B Pure LLM (Feed PDFs to GPT via RAG)

Stuff protocol PDFs into context via retrieval-augmented generation. Ask the LLM to evaluate trainee actions and generate scenarios.

✓ Pros:
Fast to prototype. Handles ambiguity naturally. Natural language feedback out of the box.
✗ Cons:
Hallucination risk on safety-critical steps — unacceptable in medical/emergency training. Non-deterministic: same action might get different evaluations on different runs. Cannot guarantee it checked every required step. May mix branches or skip steps while sounding confident.

Verdict: Insufficient alone. RAG can retrieve the correct protocol section, but it does not guarantee the generated guidance follows the required procedural flow.

Approach C Hybrid Architecture — Structured Backbone + LLM Interface SELECTED

Use LLM to help extract protocols into structured format → rule engine for deterministic compliance checking → LLM for scenario generation, natural language interaction, and feedback.

✓ Pros:
Safety-critical steps verified deterministically. LLM handles creative parts (scenarios, feedback, conversation). Scales: LLM-assisted extraction is 10× faster than manual. Separation of concerns is clean and publishable.
✗ Cons:
More complex to build. Requires defining a protocol representation format. Two systems to maintain (rule engine + LLM integration).

Verdict: This is the recommended architecture. It separates protocol correctness (deterministic, verifiable) from language generation (flexible, natural). This separation is the core architectural insight of the thesis.

3. The Hybrid Architecture

3.1 Five-Layer Architecture

LayerNameRoleWhat It ContainsDeterministic?
1 Knowledge Layer Source of truth Protocol PDFs, SOPs, guidelines, flowcharts, instructional materials. These documents remain the authoritative reference. N/A (static data)
2 RAG Layer Evidence retrieval Vector store of protocol chunks. Retrieves relevant protocol sections based on current step, decision point, or trainee error. Provides grounding and traceability for all feedback. Semi (retrieval is consistent but ranking may vary)
3 Structured Protocol Layer Machine-readable protocol representation Protocols converted from free text into decision trees, state machines, or structured JSON. Defines: required steps, allowed order, preconditions, branches, critical failures, timing constraints. YES — this is the core thesis artifact
4 Logic Layer Protocol compliance enforcement Tracks scenario state. Evaluates trainee actions against structured protocol. Checks: correct branch chosen? Mandatory step skipped? Forbidden action? Timing violated? Critical failure triggered? YES — deterministic rule evaluation
5 LLM Layer Natural interaction & generation Scenario narrative, trainee interaction, hints, explanations, debrief generation. The LLM does NOT decide protocol correctness. It receives correctness judgments from the Logic Layer and renders them in natural language. NO — non-deterministic, creative
Key Principle: The LLM never decides whether a trainee action is correct or incorrect. The Logic Layer makes that determination using the Structured Protocol. The LLM only communicates the result and generates scenarios — it is the mouth, not the brain, for protocol truth.

4.1 Canonical Format Decision

HL7 FHIR PlanDefinition Healthcare standard, citable, interoperable, recognized in literature Complex spec, steep learning curve, verbose XML/JSON MAP TO LATER for thesis write-up

Decision: Start with a custom JSON schema that captures exactly what the VR engine needs. If the thesis requires standards compliance, map the JSON to FHIR PlanDefinition for the written dissertation. The JSON schema itself is the novel contribution — no such schema exists for emergency protocols.

4.3 Extraction Process

1

PDF Ingestion

Feed protocol PDF (or image of flowchart) to GPT-4o with vision. Prompt: "Extract the decision tree from this protocol. For each step, identify: step name, type (assessment/action/decision), conditions, branches, and expected outcomes. Output as JSON."

2

Raw Extraction Output

LLM produces a draft JSON structure. This will likely have errors — missing branches, ambiguous conditions, hallucinated steps.

3

Human Validation & Correction

Non-negotiable step. A domain expert (or the thesis author using the source document) reviews every extracted step, condition, and branch against the original protocol. This is safety-critical — hallucinated steps in a medical training protocol are unacceptable.

4

Schema Validation

Automated JSON Schema validation ensures the output conforms to the defined schema. Checks: all steps have IDs, all branches have valid targets, no orphan nodes, all critical failures are flagged.

5

Graph Completeness Check

Algorithmic verification that the protocol graph is complete: every path leads to a terminal state (triage tag, task completion), no infinite loops, all conditions are mutually exclusive and collectively exhaustive at each branch point.

Scaling Estimate: With LLM-assisted extraction + human validation, a protocol with ~8 decision nodes (like SALT) takes approximately 2–4 hours to extract and validate. A complex protocol like NASEMSO Chest Pain (~20+ nodes) takes 1–2 days. This is roughly 10× faster than pure manual extraction.

5. Scenario Generation from Protocol Graphs

The Core Insight

The protocol IS the scenario template, inverted.

  • The protocol says: "IF the patient has no pulse → start CPR"
  • The scenario generator's job: "Create a patient WITH no pulse, so the trainee MUST start CPR"

This is essentially coverage-driven test generation applied to training. The protocol graph defines all possible branches; the scenario generator creates world states that exercise specific branches.

Generation Algorithm

1. Parse the protocol graph → enumerate all leaf nodes (terminal outcomes)
2. For each leaf: trace backward to find the conditions that lead to it
3. Each unique condition path = one "patient profile" or "scenario variant"
4. Compose a scenario by selecting a subset of profiles based on:
   a. Training objective (which branches to test)
   b. Difficulty level (number of patients, ambiguity, time pressure)
   c. Trainee weakness areas (from prior session data)

Difficulty Scaling

DifficultyPatientsPresentationsDistractorsTime PressureDynamic Events
Easy3Clear-cut, one protocol branch eachNoneRelaxedNone
Medium8Some ambiguous (borderline vitals)Bystanders, noiseModerateOne patient deteriorates
Hard15+Ambiguous, overlapping symptomsHeavy (family members, media)SevereMultiple deteriorations, aftershocks, secondary hazard

What the LLM Adds to Scenario Generation

  • Narrative context: "A magnitude 6.2 earthquake struck at 2:14 PM. A 3-story parking garage has partially collapsed. You are the first arriving EMS unit."
  • Patient backstories: "Patient C is a 67-year-old woman, partially buried under concrete debris, conscious but disoriented."
  • Dynamic events: "An aftershock hits. The east wall shows new cracks. Patient B stops breathing."
  • Environmental variation: "It's raining. Visibility is poor. The parking garage has no power."

The LLM generates the narrative layer while the protocol graph defines the logical layer. The LLM cannot change the protocol requirements — it can only change the story around them.

6. Runtime Compliance Checking

Event-Driven Architecture

During VR training, every trainee action is logged as a structured event:

[00:12]  APPROACH    patient_B
[00:15]  ASSESS      patient_B.breathing → YES
[00:18]  ASSESS      patient_B.pulse → YES
[00:21]  ASSESS      patient_B.mental_status → "follows commands"
[00:22]  TAG         patient_B → DELAYED ✓
[00:25]  APPROACH    patient_D
[00:30]  TAG         patient_D → IMMEDIATE ✗ (skipped hemorrhage check)

The Logic Layer (FSM) walks the protocol graph alongside the trainee. For each patient interaction:

  1. Loads the protocol FSM with the patient's ground-truth parameters
  2. Expects the trainee to follow the step sequence dictated by the protocol
  3. For each trainee action: checks if it matches the expected next step
  4. If it does: advance the FSM state, continue monitoring
  5. If it doesn't: log the error type (see Section 8), continue tracking to catch subsequent errors
  6. When a triage tag is applied: compare to expected outcome from protocol graph
⚠ Design Note: The FSM should NOT stop on first error. It continues tracking so it can report all errors at debrief — not just the first one. The FSM tracks both the "ideal path" (what should have happened) and the "actual path" (what did happen) simultaneously.

7. The LLM Layer: What It Does and Doesn't Do

LLM Does ✓LLM Does NOT ✗

Produce natural-language debrief from structured error logDecide which protocol step comes next
Provide hints when trainee is stuck ("What should you assess next?")Override the Logic Layer's compliance judgment
Generate adaptive event injections ("An aftershock just hit")Invent protocol steps that don't exist in the structured protocol
Handle edge cases where trainee does something unexpectedEvaluate safety-critical decisions independently

Debrief Generation Example

The Logic Layer produces a structured error log:

{
  "session_id": "s_20260310_042",
  "protocol": "SALT-triage-v2",
  "patients_assessed": 5,
  "correct_triage": 4,
  "errors": [
    {
      "patient": "patient_D",
      "error_type": "STEP_SKIPPED",
      "missed_step": "check_hemorrhage",
      "trainee_action": "TAG → IMMEDIATE",
      "expected_action": "ASSESS → hemorrhage",
      "triage_correct": true,
      "critical_failure": true
    }
  ],
  "timing": { "total_seconds": 187, "avg_per_patient": 37.4 }
}

This is passed to the LLM with a system prompt instructing it to generate a debrief. The LLM outputs:

"You correctly triaged 4 of 5 patients in 3 minutes 7 seconds — good pacing. However, on Patient D you tagged IMMEDIATE without first assessing for major hemorrhage. While your triage category was correct in this case, skipping the hemorrhage assessment is a critical failure: in a real MCI, you could miss a treatable bleed on a patient who should be re-categorized. Per the SALT protocol, Step 3 requires: 'Assess for and control major hemorrhage before assigning triage category.' Focus on completing the full assessment sequence even when the answer seems obvious."

Note: the feedback cites the protocol, explains why the error matters in context, and gives actionable guidance — but the determination of what was wrong came from the Logic Layer, not the LLM.

8. Types of Protocol Compliance Checks

The Logic Layer must handle several distinct types of protocol violations. Each has different computational properties:

Check TypeDescriptionExampleComputationSeverity
Step Ordering Did the trainee perform steps in the required sequence? "Checked pulse before checking breathing" Sequence comparison against expected order Moderate
Mandatory Step Omission Was a required step skipped entirely? "Never applied tourniquet" Set membership: required steps ⊆ performed steps? High
Branching Correctness Did the trainee take the correct branch based on observed conditions? "Patient has no pulse — trainee tagged DELAYED instead of starting CPR" State-dependent evaluation: (patient state × protocol graph) → expected branch High
Timing Constraint Was a time-sensitive step performed within the allowed window? "Tourniquet applied after 3 minutes (limit: 60 seconds)" Temporal comparison: timestamp(action) − timestamp(trigger) ≤ max_duration Moderate–High
Critical Failure Was a safety-critical action violated? "Moved patient with suspected spinal injury without immobilization" Hard constraint: IF action ∈ forbidden_actions(current_state) → CRITICAL CRITICAL
Unnecessary Action Did the trainee perform an action not required by the protocol? "Performed full vitals on an obviously deceased patient" Action ∉ expected_actions(current_state) AND action != harmful Low (informational)
Final Outcome Is the final triage tag / decision correct? "Tagged DELAYED but patient is IMMEDIATE" Compare trainee output to protocol-derived expected output High

9. Adaptivity & ITS Feedback Loop

What separates this system from a simple compliance checker is the adaptive feedback loop — the system modifies future scenarios based on trainee performance. This is what makes it an Intelligent Tutoring System (ITS).

11. Trainee Input: VR Events vs. Natural Language

A key design question: how does the system know what the trainee is doing?

ApproachHow It WorksProsConsNLU Difficulty
VR Object Interactions RECOMMENDED Trainee physically performs actions in VR: walks to patient, presses "check breathing" button, applies triage tag. Each interaction fires a structured event. Unambiguous. No NLU needed. Actions map 1:1 to protocol steps. Easy to timestamp. Requires building VR interaction for every protocol step. Less natural for verbal protocols (SBAR, ISBAR). NONE
Voice Commands (STT → structured action) Trainee speaks: "Checking breathing on Patient B." STT transcribes, NLU maps to structured action. More natural for communication-heavy protocols. Enables verbal patient interaction. STT errors. NLU mapping is non-trivial. Ambient noise in VR/real training. Latency. MODERATE
Hybrid Physical actions for physical steps (approach, tag). Voice for verbal steps (situation reports, patient questioning). Best of both. Natural and complete. Covers both physical and verbal protocols. Two input systems to build and integrate. MODERATE
Recommendation: Start with VR Object Interactions only (Phase 1). This eliminates NLU complexity entirely — every trainee action is already a structured event. Add voice input in Phase 2 for virtual patient dialogue and verbal reports.
